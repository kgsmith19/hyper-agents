# Hyper-Agents V1 design

## Shape

```
CLI / hooks / webhook / daemon / remote adapter      (interfaces, P06)
        │  RunRequest
        ▼
Controller: admission → TeamSelector → workflow state machine     (application, P04)
        │  MintRequest (grants, budgets, exact repo@sha)
        ▼
ExecutorPort ──► OpenHandsExecutor (Docker workspace)  |  FakeExecutor (offline)   (adapters, P03)
        │  events + Receipt
        ▼
RunStore (SQLite WAL, append-only events)   ReviewService / VerificationService (P05)
```

Dependency direction: `domain` ← `application` ← `adapters` / `interfaces`.
`tests/conformance/test_dependency_direction.py` enforces it.

## Roles and ownership boundaries

| Role | May | Never |
| --- | --- | --- |
| **Planner** | Write a specification and acceptance criteria | Edit source; approve |
| **Builder** | Edit task-scoped source and tests in its own worktree | Review or verify its own work; publish |
| **Reviewer** | Read an immutable snapshot; emit findings with stable IDs | Write anywhere, hold a write or publish credential, or propose code |
| **Verifier** | Run trusted checks against an exact SHA; emit a hashed receipt | Repair; run Builder-authored commands without validation |
| **Controller** (code) | Own transitions, grants, approvals, retries and stop conditions | Be a language model |

Personas and instructions are **advisory**. Authority is a structured grant enforced by the sandbox,
mounts, network policy and credentials, never by prompt text.

## Executable acceptance

A task is admitted only with a non-empty `AcceptanceContract` (`domain/acceptance.py`). Each criterion
names the deterministic `check` the Verifier runs. An empty list, a missing check, or a duplicate or
malformed ID is rejected as `invalid_input`.

## Event envelope and versioning

Each state change is one immutable `EventEnvelope` (`domain/events.py`):
- `schema = "hyper-agents.event/v1"`;
- `run_id`, a per-run `sequence`, a dotted `type`, a timezone-aware `occurred_at`;
- `idempotency_key`, an optional exact `head_sha`, and a redacted `payload`.

A reader refuses an unknown `schema` instead of guessing. A breaking change mints `…/v2`, and readers
for each supported version live side by side. Additive optional fields do not bump the version.

## Error taxonomy

`domain/errors.py` defines eight categories: `invalid_input`, `policy_denied`, `budget_exhausted`,
`stale_state`, `provider_unavailable`, `worker_failed`, `cancelled` and `internal`. Only
`provider_unavailable` and `worker_failed` are retryable, within bounded attempts with exponential
backoff and jitter. Messages carry no secret values or repository content.

## Cancellation

Cancellation is a controller event. The executor then:
1. stops the worker process tree and its container;
2. revokes the worker's credential lease;
3. writes a cleanup receipt.

A run is `cancelled` only after the receipt exists. Timeouts take the same path.

## Leases and idempotency

- Each task claim is a lease with a heartbeat. A lost heartbeat releases the claim, and recovery
  re-reads state before acting.
- Delivery is at-least-once. Every side effect carries an idempotency key, and the RunStore refuses
  a duplicate key (`RunStorePort.append` returns `False`). Exactly-once remote actions are never
  claimed.
- Each worker gets a fresh context and a unique workspace per mint.

## Secrets

- Credentials come from a short-lived broker lease at mint time, scoped to the role.
- A Reviewer never receives a write or publish credential.
- No secret appears in YAML, logs, images, Issues, snapshots or the repository; a
  `tests/security` scan enforces this.
- Local deployments read keys from a gitignored `.env`.

## Model budgets

Each mint carries token, cost (USD), wall-clock and iteration limits. Exhausting any of them ends the
worker with `budget_exhausted`, which is never retried automatically. Per-role preferred provider tiers
live in the role catalog (P02). R2/R3 work needs a Reviewer from a different provider family when one
is available.

## V1 non-goals

These are out of scope for V1:
- Kubernetes, multitenancy, and always-on per-role models;
- model training and a bespoke web UI;
- unlimited dynamic role creation;
- OpenHands automation as a hard dependency;
- any cloud hosting: V1 is one trusted local host.

## Owner setup still required

Repository settings are owner-only. These are the exact steps:
1. **Settings → General → Pull Requests:** enable "Allow auto-merge".
2. **Settings → Rules → Rulesets → New branch ruleset** for `main`, with these rules:
   - require a pull request;
   - require the status check `PR Gate`;
   - block force pushes and deletion.
3. **Optional:** add `.github/CODEOWNERS` covering `ci/` and `.github/`, once this repository has a
   second maintainer identity.

Until step 2 is done, `PR Gate` is advisory, and the owner merges by hand.
